# Authentication and security

## Release boundary

Default configuration remains a labelled browser-local demo. This workspace now enables authenticated Supabase accounts for development through explicit storage/account flags. Hosted migrations/isolation/reward checks and user-observed Google login, persistence, two-account privacy, sign-out, offline retry, and browser focus refresh have passed. The user also confirmed all-device sign-out required sign-in in both browsers and saved progress returned afterward. Actual token-expiry renewal, a direct hosted revoked-token API probe, and committed-save/lost-response recovery remain pending; production accounts stay gated. See [the evidence and remaining acceptance criteria](SUPABASE_INTEGRATION.md).

## Verified identity and commands

Separate browser/server Supabase clients use cookie-based SSR. Next.js `proxy.ts` refreshes sessions with `getClaims()` and carries refreshed cookies through redirects. The journey API independently calls `getUser()` and checks `account_session_active()` before every read/write. Protected pages also check active sessions after claims verification. OAuth callback code exchange is followed by verified user lookup; redirects use the configured canonical origin rather than caller-supplied targets. Current-device sign-out remains available; Profile also offers a separately confirmed all-device sign-out. Mutation endpoints require the exact configured Origin and bounded, strictly validated input.

Database commands derive their actor from `auth.uid()`, lock the profile row and execute atomically with a fixed search path. Clients supply an activity, not an authoritative snapshot, user ID, XP amount, completion date or achievement list. Reading rewards require all assigned chapters; book, quiz and reflection rewards have stable unique keys. A wrong first quiz attempt cannot become a correct rewarded retry. Activity dates use PostgreSQL's saved IANA timezone. Timezone/plan changes are prohibited after activity.

The first two migrations create schema/RLS and complete reference data. Migration 003 adds trusted commands and revokes direct profile/reflection writes. Migration 004 seeds six reviewed quiz prompts and private solutions. Migration `20261016142344` enforces live session checks in commands and restrictive personal-table SELECT policies. Personal tables expose owner-only reads. Client roles cannot execute private helpers or read answer keys; submitted attempts expose their own feedback. Group membership does not grant journal access.

## Persistence and errors

Authenticated progress and journals are database-backed. The account provider neither writes personal snapshots to localStorage nor silently falls back to demo storage. It does not automatically upload existing demo journals. Requests and OAuth responses use private/no-store cache controls; account data is fetched per verified session. Database error details are sanitized. After a failed or uncertain save, **Check saved progress** reads the latest server snapshot without replaying the mutation or reloading the page; a later intentional retry still uses the idempotent command layer.

Identity verification failures distinguish invalid/missing sessions (401) from retryable connection errors, upstream failures and rate limits (503). Only 401 sends the account browser back to login. A protected page whose identity service is unavailable fails closed with a non-cacheable 503 while retaining response cookies; it does not render private content or discard the session because of an outage.

Account exports use `GET /api/account/export` with independent `getUser()` verification, the caller-session `get_journey` RPC, and schema validation. Success returns an attachment with private/no-store, Cookie variation and nosniff headers. The browser fetches and validates a fresh snapshot before creating a download; errors never fall back to the already displayed snapshot. Exported JSON contains journey data, not session tokens or privileged keys. Demo export remains local. Both modes now support explicit previewed backup merges; see [backup/restore](BACKUP_AND_RESTORE.md). Automatic backups are not configured.

A Supabase publishable/legacy anon key is suitable for the client. A database password or secret/service-role key must never be placed in `NEXT_PUBLIC_*`, committed, or shared in chat. Google client secrets belong in Supabase provider configuration. The Next.js runtime does not need privileged database credentials. The account-deletion Edge Function uses Supabase-injected administrative credentials only inside its hosted runtime. CLI migrations/live tests require a separate explicitly confirmed development connection and verify its project reference.

## Validation and remaining gates

Embedded PostgreSQL tests execute all migrations and test two identities, anonymous access, direct-write restrictions, rewards, quiz secrecy, achievements and group/journal isolation. HTTP/session tests mock the SDK to exercise verification, Origin checks, command validation, redirects, refresh-cookie propagation and sign-out. Neither test layer proves hosted Google login, token expiration or device synchronization.

Before production accounts: apply/test migrations on the selected development project; verify Google consent/callback settings; complete real login/logout and session-renewal checks; verify independent-user journal isolation and cross-device persistence; review account deletion, backup, rate limits and operational monitoring. The live database script uses synthetic fixtures inside a rolled-back transaction, without deleting existing users.

## Demo privacy

Demo data belongs to a browser profile/origin, not a signed-in person. It is not encrypted or synchronized and is accessible to someone with access to that browser. State validation is not tamper resistance; demo quiz solutions are inspectable. Multi-tab writes use Web Locks where available, with a latest-snapshot fallback elsewhere. Export is explicit and no automatic import or sharing occurs. Paid AI remains absent.

## Active sessions and all-device sign-out

Following [Supabase session guidance](https://supabase.com/docs/guides/auth/sessions), the database checks the signed `session_id` against the same user’s `auth.sessions` row and rejects a missing/malformed ID, a deleted session, or an elapsed `not_after`. It does not inspect refresh tokens or change hosted JWT lifetimes, inactivity limits, provider settings, or plan settings. Completed/in-flight responses and previously downloaded files cannot be withdrawn; existing UI state is replaced on the next account refresh/navigation.

`POST /auth/signout-all` validates an exact Origin, a bounded 1 KiB form with one fixed confirmation field, current identity and session. It calls the normal SSR SDK’s global sign-out and reports success only after that call succeeds. Personal journey data is retained. No user ID, access token, secret key, or arbitrary scope comes from the submitted form. Cancellation does not call Auth.

The new boolean helper intentionally uses SECURITY DEFINER to read the managed Auth session table without granting clients access to that table. It has an empty search path, no parameters, signed-claim ownership checks, and execute privileges only for authenticated clients. The [authenticated SECURITY DEFINER advisor](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) therefore lists eight intentional API functions. Private answer-table RLS remains deny-by-default. Existing leaked-password-protection and reference-foreign-key performance advisories are documented in the integration runbook; no production-readiness claim is made.

## Permanent account deletion

The account-only UI explains deletion, encourages a private export, requires typing `DELETE MY ACCOUNT`, and supports cancellation. The app API enforces exact Origin and a streamed 1 KiB JSON limit, accepting only the confirmation field. A caller cannot provide another user ID. The backend function independently verifies the caller through Auth, matching JWT claims and the live session. A signed OAuth AMR timestamp must be within ten minutes, with thirty seconds of future clock tolerance. A fresh `iat`, token-refresh AMR or user-editable metadata cannot satisfy recent login.

The [Auth Admin deletion API](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser) runs only in the hosted function using [Supabase-injected Edge credentials](https://supabase.com/docs/guides/functions/secrets). Platform JWT verification remains enabled. There are no browser CORS permissions and browser-origin requests are rejected. Global revocation must succeed before deletion is attempted. All responses are private/no-store; upstream errors and credentials are never returned. The Next.js runtime never receives the administrative key.

Existing FK cascades remove app personal records, membership rows and owned groups. Shared Scripture/quiz reference data and another user's journey remain intact. No Storage upload feature exists; owned Storage objects would need explicit cleanup if that feature is later added because Auth deletion can otherwise fail. Before enabling fellowship creation, review group ownership transfer/closure: the existing owner cascade deletes an owned group and its memberships. Signing into FaithQuest after successful deletion can create a new empty account; deletion does not remove the Google account, provider consent, downloaded exports, or promise erasure from provider logs/backups outside the live app tables.

Deletion is irreversible; revoke-plus-delete is a sequence of Auth operations rather than one cross-service transaction. Partial/uncertain failures are reported honestly and may leave a retained account signed out. Automated checks use mocks, a local SDK protocol fixture, synthetic browser accounts and rolled-back database fixtures. Real disposable-account deletion acceptance remains pending. Existing operational backup, retention, rate-limit and monitoring work remains a production gate.

## Request limits and private reporting

Seven hosted migrations are applied. Public command wrappers enforce the active session, existing profile lock and persistent per-account budgets; moving the unmetered implementations into `private` does not grant access to them. Reads returning snapshots from commands count toward the read allowance. Export and account-health routes have separate admission calls; deletion version 2 checks its budget inside the hosted function, so direct function invocation cannot bypass it. The caller supplies no quota size, time or identity. Full limits and operational constraints are in the integration runbook.

The counter table has RLS enabled, no client grants/policies and an Auth-user deletion cascade. Upserts are atomic across app instances. These are fixed windows, with possible bursts across boundaries. Committed command calls count even for idempotent retries; invalid/rolled-back commands do not consume a persistent command allowance. A write denial rolls back its transaction; no XP or save success is invented. Independently budgeted reads still allow saved-progress recovery. These controls do not cover unauthenticated network floods or every direct owner-only Data API SELECT; gateway/IP limits remain production work.

Only generated incident references, an allowlisted operation, status, generic category and UTC time enter the application reporter. It accepts no raw error, request, payload, email, user ID, URL or token. Repeated events share a recorded reference for thirty seconds instead of creating an unbounded log stream. Provider access/audit/database logs have their own policies and retention; this application logger does not promise to sanitize provider-managed logs. No external reporting or alert-delivery service is enabled.

Public readiness reports a status enum only, probes public Auth/catalogue endpoints with bounded timeouts, coalesces concurrent checks and briefly caches only booleans. Authenticated connection checks verify the current identity/session and return no snapshot. Error responses are private/no-store with support references; rate responses include a bounded Retry-After. Client account fetches time out after fifteen seconds, preserve an uncertain outcome and never automatically retry a mutation.

Post-DDL advisors show nine intentional authenticated SECURITY DEFINER APIs and two private RLS tables without policies. The [SECURITY DEFINER finding](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) is reviewed: these functions require fixed search paths and signed ownership/session checks; private implementations are not client executable. The [no-policy notices](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy) intentionally deny access to quiz answers and request budgets. Existing [leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) and [three reference foreign-key indexes](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys) remain for production review.

## Explicit backup import

Restore is authenticated data entry, not proof that an export was server-issued. The file is previewed locally and the user explicitly confirms ownership and the destination account before private reflections are uploaded. No automatic demo migration occurs. The 5 MiB endpoint, strict normalized schema, live identity/session, exact Origin, fixed timezone and direct-RPC validation protect the boundary. Actor IDs, profile settings, ledgers, correctness flags and answer keys are not accepted. All SQL is parameterized; the SECURITY DEFINER function uses an empty search path and only authenticated execute permission. Private helper/counter/answer access remains revoked.

Existing chapters, first attempts and reflections cannot be overwritten through restore; unique rewards are derived server-side. Historical self-reported activity can recover old calendar dates, an intentional import exception to ordinary today-only reflection creation. Backups are not signed, encrypted, automatically verified as belonging to a particular person, or retained by the app after import. Restoring another person's file would copy their private text into the selected account, so the privacy/ownership confirmation is explicit. Three successful operations/fifteen minutes plus the shared write/read limits bound restore work; unsuccessful transactions roll back. No full-service disaster-recovery claim follows from personal imports. Details and operational gates are in [backup and restore](BACKUP_AND_RESTORE.md).

## Saved verse privacy

Saved references are personal account data, with caller-only reads, active-session enforcement, no group-based visibility and no direct client mutation grants. Protected `/study` navigation and the existing independently verified journey/export/restore routes apply. The public save/remove RPC accepts only book/chapter/verse and explicit boolean intent: ownership, available numbering, collection limits, timestamps and quota admission are enforced in PostgreSQL. It never accepts caller-supplied text or XP. Repeating a save/removal cannot toggle another way or grant a reward. Private account selections are not persisted in localStorage.

Version 1 backup support normalizes saved references and ignores imported timestamps; invalid references, empty source placeholders or a merged cap overflow reject the entire import. User deletion cascades saved references, while another user's collection remains intact. Hosted rollback-only tests exercise these boundaries with synthetic users. Post-DDL advisors list eleven intentional authenticated SECURITY DEFINER APIs, two intentionally inaccessible private RLS tables, and the existing password/reference-index review items. The new table's foreign keys are indexed. Review [the intentional function notice](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [private-policy notices](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), and [reference-index notices](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys). These checks do not close the separate production/OAuth recovery gates.

## Journal tools privacy

Journal categories use the existing caller-private reflection table and session-restricted reads. The new save RPC has an empty search path, explicit authenticated-only EXECUTE, verified actor/profile lock, bounded validation and shared write/read quotas. Anonymous/revoked sessions and direct writes remain denied. Drafts exist only in journey-layout memory and are cleared on leaving it; they never reach localStorage/sessionStorage or account exports. Search terms stay in component state and are not sent to the server or URLs. Draft protection is not durable autosave or a guarantee against simultaneous remote writes. See [JOURNAL_TOOLS.md](JOURNAL_TOOLS.md).

## Private reading challenges

The challenge page is in both session-protected route lists and the account provider's active-page list. Enrollment has owner/session RLS, authenticated-only SELECT and no direct writes. Its join command uses an empty search path, explicit authenticated-only execution, the existing live actor/profile lock and write/read budgets; the reward helper remains private and inaccessible to clients. No actor ID, clock, start date or XP can enter the normal join command. Account deletion cascades remove enrollments.

Backup enrollment dates are self-reported recovery data and are checked again server-side: valid, nonfuture, at most 1,000, nonoverlapping both internally and with the saved union. All validation precedes any chapter/journal/period mutations. Bonuses derive from authoritative merged mission dates and unique keys, without granting a caller-provided reward. Joining fixes timezone changes. Challenge history, dates and rewards are never shared with groups or other readers. The existing deployment/identity/operational gates remain open.

## Invite-only fellowship

Live Community requires an account and explicit consent before create/join. The shared summary is limited to current display name and rounded overall plan percentage, plus structural group fields and owner-only controls. Personal table RLS is unchanged; journal/prayer content, saved verses, exact reading dates, quiz results and XP are never added to group responses. Existing memberships receive no automatic sharing consent. Owners are authorized by stored owner_id against the live caller, never by user metadata or client-supplied role.

The new API checks live sessions, exact Origin on writes and streamed 4 KiB/strict-schema bounds. Routines use caller/profile locks, consistent group lock order, invitation rechecks and private metadata. Random UUID-based invitation codes are owner-only through the API and never placed in URLs, application logs or personal exports. Removing a member rotates the invitation; they could rejoin only with a new valid code and consent. Revocation/leave/closure stops future reads, without erasing previously viewed data. Refresh is explicit/on focus, not a realtime guarantee.

Creation request IDs bind replay protection to the caller and survive group closure as null-target tombstones; they do not grant access. Safe domain errors are allowlisted and commit shared admission charges, including invalid full-format invitations. Account exports include own membership metadata, with no invitation or other-member roster. Personal restore ignores this metadata and cannot create/join groups. Account deletion removes memberships and closes owned groups while preserving other people's personal journeys.

All seven synthetic hosted scripts passed inside BEGIN/ROLLBACK; no real memberships were created or removed. Advisor findings and review links are recorded in the integration runbook. See [policy/testing](FELLOWSHIP_GROUPS.md).

## Plan selection boundary

Authenticated `select_reading_plan(text)` accepts only known published schedule versions, derives the caller from the active session and serializes selection with activity through the existing profile lock. Direct profile updates remain denied. Activity locks plan identity; a stale selection returns an allowlisted conflict without resetting history. Backups cannot select a plan and must match the destination version before writes. Shared quiz eligibility requires a reviewed question, a published source plan and its reference chapter in the active schedule. The source publication boundary is checked again for imports. No new table or personal-read grant was introduced; the intentional authenticated definer command is included in the documented [advisor review](SUPABASE_INTEGRATION.md#reading-plan-choice-integration-18-october-2026).

## Private verse annotations

Notes extend owner/session-protected saved-verse rows and never enter fellowship responses. Direct writes remain revoked. The note RPC derives the actor, locks that profile before the shared write budget, compares the expected saved text and returns a metered snapshot. Safe stale/missing/removal conflicts disclose no saved text in errors. A saved reference with a note cannot be removed until the note is explicitly deleted, including through direct RPC calls. Revoked and anonymous sessions remain denied; profile/account deletion cascades to note-bearing saved rows.

Drafts live only in the journey-layout memory provider, stay out of web storage, URLs, exports and requests until explicitly saved, and warn before reload/close. Unsaved text survives internal filters/navigation and uncertain writes; a response clears only its captured draft, preserving newer typing. Backup normalization strips note timestamps and the database preserves destination notes on conflicts. The whole restore validates before writes. See [the data and testing contract](STUDY_TOOLS.md#private-verse-notes).
